MenuCreator por dentro: una carta digital con servidor, desplegada gratis

Cómo está hecho MenuCreator, una carta digital para restaurantes en Nuxt con su propio servidor. Un editor de prueba que reutiliza el panel real sin tocar la base de datos, un registro que la interfaz cerraba y el servidor no, las fotos dentro de la base de datos, lo que Vercel y TiDB no avisan, colores de marca que se ajustan solos al contraste y un guardado automático pensado para el servicio.

menucreatorarquitecturanuxtvuetypescript

MenuCreator es una carta digital para bares y restaurantes. El hostelero la edita desde un panel y el comensal la abre en el móvil con un QR. Es un proyecto personal y está publicado en menu.abdell.dev. Los primeros commits son de marzo de 2025, pero casi todo lo que hay hoy se hizo entre finales de octubre y noviembre de 2026. Cómo se usa lo cuento en la guía, y el panel se puede probar sin cuenta en /prueba.

Es mi primer proyecto del blog con un servidor escrito por mí. Cuentas, sesiones, base de datos y despliegue, todo en un plan gratuito. Este artículo va de las decisiones que eso trajo, empezando por la más visible.

El mapa

  • Cliente: Nuxt 3, Vue 3.5 y Tailwind CSS 4, sin librería de componentes.
  • Servidor: las rutas de Nitro. better-auth gestiona las sesiones y los roles admin y hostelero, Drizzle ORM habla con MySQL y Zod valida todo lo que entra.
  • Despliegue: Vercel en el plan gratuito, la base de datos en TiDB Cloud Serverless (compatible con MySQL) y el DNS en Cloudflare.

Una edición viaja así: el hostelero cambia un plato en /admin/menu, el composable useMenuAdmin() llama a /api/admin/*, un middleware comprueba la sesión, la ruta valida con Zod y escribe con Drizzle. La carta pública, en /<slug>, lee de /api/restaurants/<slug> y no pinta los platos agotados.

Un editor de prueba que no puede romper nada

El registro está cerrado, así que quien llegaba desde el portafolio solo podía ver cartas. El editor, que es la parte que más luce, no lo podía tocar nadie.

Había tres caminos. Una cuenta de demo compartida tenía dos problemas: los visitantes verían lo que escriben otros, contenido ofensivo incluido, y hacía falta resetearla cada noche. Unas capturas o un vídeo eran lo más barato, pero también lo menos convincente. Elegí el tercero: el panel real, con los datos en el navegador.

La regla era que no hubiera dos copias de las pantallas. Si el editor de prueba se separa del real, con el tiempo enseña algo que ya no existe. Así que /prueba, /prueba/carta y /prueba/diseno no tienen páginas propias: son alias de rutas de las tres de /admin.

// app/pages/admin/menu.vue
definePageMeta({
  layout: 'admin',
  // Same screen for "Prueba el editor" (in-browser data, see useMenuAdmin)
  alias: ['/prueba/carta'],
})

Todas las pantallas leen y escriben a través de un único composable, y lo único que cambia es de dónde salen los datos:

// app/composables/useMenuAdmin.ts
export function useMenuAdmin() {
  const { isSandbox } = useSandbox()
  return isSandbox.value ? useSandboxMenuAdmin() : useServerMenuAdmin()
}

Las dos ramas devuelven la misma interfaz (sections, saving, addItem, updateItem, reorderSections, uploadImage…). La de prueba trabaja sobre una copia de la carta de /demo, la guarda en sessionStorage para que sobreviva a una recarga y convierte las fotos en data URL, con el mismo límite de 4 MB y los mismos formatos (JPG, PNG y WebP) que la subida real. El fichero empieza con una regla escrita: this file must never call $fetch or any /api route. La lógica pura (añadir, reordenar, serializar) está separada en app/lib/sandboxMenu.ts, que es lo que cubren los 13 tests del repo.

Lo que costó salió en un detalle. Con varias fotos, sessionStorage se llena. La primera versión, al fallar la escritura, se quedaba en silencio con la copia anterior, y al recargar el visitante volvía a un estado viejo. Ahora, si no cabe, se guarda la carta sin las fotos subidas en el navegador. Además, el guardado espera a que dejes de escribir y se fuerza al cerrar la pestaña, en vez de serializar varios megas en cada pulsación.

La puerta que la interfaz cerraba y el servidor no

La aplicación no tiene página de registro: las cuentas las crea el admin. Pero better-auth monta sus propias rutas, y POST /api/auth/sign-up/email seguía respondiendo. Cualquiera con curl podía crearse una cuenta de hostelero y, con la subida de fotos ya funcionando, llenar la base de datos gratuita.

Esconder un botón no cierra una ruta, así que la cerré en el servidor:

// server/middleware/auth.ts
if (event.path.startsWith('/api/auth/sign-up')) {
  throw createError({
    statusCode: 403,
    statusMessage: 'El registro está cerrado',
  })
}

La semilla y la pantalla de Usuarios crean cuentas llamando a auth.api directamente, sin pasar por HTTP, así que no les afecta.

El login por enlace mágico sigue el mismo criterio. Sin clave de Resend, la pestaña no aparece, y si alguien llama a la ruta igualmente, en producción da error en lugar de fingir que se ha enviado un correo.

Desplegar gratis, a escala de demo

Quería publicarlo sin pagar nada, así que monté Vercel Hobby, TiDB Serverless y Cloudflare. Ese entorno trajo tres decisiones.

Las fotos, dentro de la base de datos

La subida escribía en public/uploads, y en Vercel el disco no se puede escribir. Tenía tres opciones: guardar las fotos en la base de datos, commitearlas en el repo o usar Cloudflare R2. R2 es lo correcto para un producto real, pero para una demo, en la que solo subo fotos yo, suponía otra cuenta, más claves y otra librería. Elegí la base de datos: una tabla image con los bytes y una ruta pública que los sirve.

El coste es que cada foto vista lee de TiDB. Como un id nunca cambia de contenido, la respuesta se puede cachear para siempre:

// server/api/images/[id].get.ts
setResponseHeaders(event, {
  'Content-Type': row.mimeType,
  // s-maxage lets Vercel's CDN keep it too; max-age alone only reaches browsers.
  'Cache-Control': 'public, max-age=31536000, s-maxage=31536000, immutable',
  'X-Content-Type-Options': 'nosniff',
})

Con s-maxage, la CDN de Vercel guarda la foto y la base de datos la lee una vez. El límite de subida bajó de 5 a 4 MB, porque Vercel rechaza peticiones de más de 4,5 MB.

Serverless no espera a nadie

La semilla crea el admin en el primer arranque. En local funcionaba. En Vercel, el admin aparecía sin cuenta de contraseña: la función se congela en cuanto envía la primera respuesta, y la semilla, lanzada sin esperar, se quedaba a medias. Ahora cada petición espera a que termine, que después del primer arranque es una promesa ya resuelta:

// server/plugins/seed.ts
const seeding = seed()
nitroApp.hooks.hook('request', async () => {
  await seeding
})

Por lo mismo, el pool de conexiones es de 2 en Vercel y de 10 en el resto de entornos. En serverless hay muchas instancias cortas, y cada una abre el suyo.

TiDB es compatible con MySQL, casi

TiDB rechaza un valor por defecto literal en una columna JSON, como DEFAULT ('[]'). Los valores por defecto de tags, allergens y theme pasaron a la aplicación:

// server/db/schema.ts
tags: json('tags').$type<string[]>().notNull().$defaultFn(() => []),
allergens: json('allergens').$type<string[]>().notNull().$defaultFn(() => []),

drizzle-kit push también lee mal la estructura de TiDB: la primera vez deja las tablas sin claves únicas ni relaciones, y las siguientes intenta borrar índices. Contra TiDB, las tablas se crean con el SQL de drizzle-kit export, y lo dejé escrito en la guía de despliegue del repo.

El despliegue se hace desde mi máquina con la CLI. Un .vercelignore impide subir los .env con secretos, y el script sube una copia limpia del último commit, sin .git y sin cambios a medio hacer.

El color del restaurante, sin romper la accesibilidad

Cada restaurante elige plantilla, colores, tipografía y esquinas. El riesgo es evidente: un hostelero elige un dorado claro para los precios sobre un fondo crema, y la carta deja de leerse.

No quería prohibir colores ni avisar con un error. La carta mueve el color de marca hacia el color del texto de la plantilla, en pasos del 5 %, hasta alcanzar el contraste de 4,5:1 que pide WCAG para el texto:

// app/utils/cartaTheme.ts
export function readableOn(color: string, bg: string, ink: string, min = 4.5): string {
  if (!hexToRgb(color)) return ink
  for (let t = 0; t <= 1.0001; t += 0.05) {
    const c = mix(color, ink, t)
    if (contrast(c, bg) >= min) return c
  }
  return ink
}

Para los rellenos, como el chip de la sección activa o los botones, hay una variante que pide 3:1 contra la página y 4,5:1 para el texto blanco o negro de encima. El hostelero ve su color, o el más cercano que se lea bien.

Los alérgenos siguen el mismo principio. Son los 14 del Reglamento (UE) 1169/2011, guardados como datos de cada plato, y en la carta se escriben con su nombre. No dependen de un icono ni de un color.

Guardado automático pensado para el servicio

Un hostelero edita la carta en mitad del servicio, con prisa y desde el móvil. Un botón de guardar es un paso más y una forma más de perder un cambio.

Los textos se guardan 450 ms después de la última pulsación. Los cambios del mismo plato se acumulan y salen en una sola petición:

// app/pages/admin/menu.vue
function debounced(key: string, updates: Record<string, unknown>, save: /* ... */) {
  pendingUpdates.set(key, { ...(pendingUpdates.get(key) ?? {}), ...updates })
  clearTimeout(timers.get(key))
  timers.set(key, setTimeout(() => {
    // ...
    persist(() => save(merged))
  }, 450))
}

Los interruptores de agotado, el orden y los alérgenos se guardan al momento, porque son un solo toque. Un indicador dice «Guardando…», «Todo guardado» o «No se pudo guardar el último cambio», y si cierras con cambios sin enviar, el navegador avisa.

La excepción es el diseño. Ahí sí hay Guardar cambios y Descartar, porque probar plantillas es jugar, y cada prueba no debería cambiar la carta que ya ven los clientes.

Cómo sé que funciona

Hay 13 tests con el runner de Node, todos sobre la lógica del editor de prueba: que la copia de la carta de ejemplo no comparte objetos con el original, que el orden se mantiene contiguo al borrar, que los datos guardados viejos o rotos se descartan y que las fotos se validan con las mismas reglas que la subida real. El resto lo cubren el typecheck con vue-tsc y la revisión a mano en la web publicada. No hay pruebas de extremo a extremo, y no voy a fingir que una suite de 13 tests cubre una aplicación con servidor.

Trabajo con IA y con un método: antes de cada cambio grande escribo una especificación, con lo que quiero, lo que no y las alternativas descartadas. El diseño, las specs y las reglas son míos; la IA implementa y yo verifico cada cambio.

Lo que queda

  • Más tests. El servidor no tiene tests automáticos. Lo siguiente serían pruebas de las 13 rutas de /api/admin, empezando por los permisos de /api/admin/users, que solo debe usar el admin.
  • Almacenamiento de objetos para las fotos, si pasara de demo a producto, y un plan de Vercel que permita uso comercial.
  • El diseño de cada sección. La base de datos guarda una disposición por sección (lista, rejilla, tarjetas o destacada), pero la carta todavía no la usa y el panel no la enseña.
  • Lo que no hace: pedidos, pagos, carta en varios idiomas o varios restaurantes por cuenta. No están, y no los anuncio hasta que existan.

El código es privado. Si quieres verlo o hablar de cómo está hecho, escríbeme. Y si quieres tocarlo, el editor de prueba es el panel real.
