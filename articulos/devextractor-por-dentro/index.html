DevExtractor por dentro: las decisiones detrás de una extensión que parece simple

Cómo está hecha DevExtractor, una extensión de Chrome en Manifest V3 con WXT y Vue. Decisión a decisión, cómo saca los SVG incrustados de una página, cómo busca en iframes, shadow DOM y carga diferida, cómo descarga y monta ZIP sin poder crear blobs y por qué el mismo código descarga en Firefox, por qué las reglas de red se ciñen a un host y a una sola petición, cómo sobrevive a un service worker que se duerme, cómo se deshace un cambio en vivo y cómo encuentra botones en Instagram sin leer textos.

devextractorarquitecturaextensionestypescriptvue

Actualizado en noviembre de 2026 para la versión 1.5.0.

DevExtractor empezó como una utilidad para no tener que copiar a mano los <svg> de una web a un bloc de notas. Pulsas un botón, te salen todas las imágenes de la página y te las bajas. Dicho así parece un fin de semana de trabajo. Es un proyecto personal, en marcha desde abril de 2026 y publicado en la Chrome Web Store. Qué hace y cómo se usa está en el manual.

Este artículo va de lo que hay debajo, decisión a decisión. Casi ninguna estuvo en la idea. Estuvieron en los detalles: que una descarga no pise a otra, que una regla de red no toque la navegación normal, que un cambio en vivo se pueda deshacer sin dejar rastro.

El mapa

Es una extensión Manifest V3 hecha con WXT, con Vue 3, TypeScript y Tailwind CSS v4. WXT genera el manifiesto y empaqueta cada punto de entrada por separado:

Cargando diagrama...

El popup y el panel de DevTools son dos páginas distintas que montan los mismos componentes (AppLayout, MediaGallery, LinkManager, FontManager). La única diferencia es de dónde sacan la pestaña: el panel usa chrome.devtools.inspectedWindow.tabId y el popup deja que el service worker busque la pestaña activa.

El content script está declarado para todas las URL, pero el service worker no se fía: antes de pedirle nada le manda un PING, y si no hay PONG lo inyecta con scripting.executeScript. Así funciona también en pestañas que ya estaban abiertas cuando se instaló la extensión.

Leer el DOM, no la red: los SVG inline

Todo empieza en utils/domParser.ts, que recorre el DOM y devuelve una lista de elementos con su URL, su tipo, su dominio y su tamaño. Podría haber escuchado la red y apuntar todo lo que la página descarga. No me servía. Un <svg> escrito en el HTML nunca pasa por la red, y era justo lo que quería sacar.

La solución es corta:

deepQuerySelectorAll<SVGSVGElement>('svg', roots).forEach((svg, index) => {
  const serialized = serializeCleanSvg(svg);
  // ...
  if (!seenUrls.has(serialized)) {
    seenUrls.add(serialized);
    const dataUrl = `data:image/svg+xml;charset=UTF-8,${encodeURIComponent(serialized)}`;
    // ...una tarjeta más, con el SVG como contenido y como data: URL
  }
});

serializeCleanSvg clona el SVG, le quita los atributos que pone la propia extensión (el id, la marca de oculto) y lo pasa a texto con XMLSerializer, con su espacio de nombres, listo para guardarse como archivo. Quitar esos atributos importa: si no, el mismo icono escaneado dos veces daría dos textos distintos y saldría repetido. deepQuerySelectorAll es el recorrido que también entra en los shadow DOM, del que hablo en la sección siguiente. Ese texto viaja con la tarjeta: la data: URL sirve de vista previa, y al descargar se crea el .svg directamente a partir del texto, sin pedir nada a la red. La clave para quitar duplicados es el propio contenido: si una web pinta el mismo icono en diez sitios, sale una vez.

Las imágenes de fondo se leen con getComputedStyle(...).backgroundImage, porque una regla de CSS no aparece en el atributo style. Y cada elemento encontrado se marca con un atributo data-devextractor-id. Ese id es lo que permite luego actuar sobre un elemento concreto (ir hasta él, ocultarlo, copiar su CSS o sustituirlo), aunque haya otros con la misma URL.

Buscar donde no se ve

La primera versión recorría document y nada más. En una web real eso deja fuera bastante. En la 1.5.0 cambié el recorrido para que llegue a cuatro sitios que antes se perdía.

El shadow DOM. Los componentes web guardan su contenido en un shadow root que querySelectorAll no atraviesa. La extracción junta primero el documento y todos los shadow roots que encuentra, anidados incluidos, y busca en todos. Los cerrados también, en Chrome, que da a las extensiones una forma de abrirlos:

// utils/deepDom.ts
export function getShadowRoot(element: Element): ShadowRoot | null {
  const chromeDom = (globalThis as any).chrome?.dom;
  if (typeof chromeDom?.openOrClosedShadowRoot === 'function') {
    try {
      return chromeDom.openOrClosedShadowRoot(element) ?? null;
    } catch {
      // Fall through to the open root
    }
  }
  return element.shadowRoot ?? null;
}

Los iframes. El content script de la página principal no ve dentro de un iframe de otro origen. Así que el service worker lanza la extracción en todos los marcos de la pestaña (allFrames: true), inyecta el script donde falte, se salta los que no contestan a tiempo y junta los resultados. Cada medio lleva el frameId del marco del que sale. Sin eso, «ubicar en página» o «sustituir» irían al documento principal y no encontrarían nada.

La carga diferida. Muchas webs ponen un GIF transparente en src y la imagen real en data-src hasta que haces scroll. Si la imagen todavía enseña el marcador, se lee la URL de esos atributos.

El srcset. Antes cogía currentSrc, la versión que el navegador había elegido para tu pantalla. Para descargar interesa la más grande, así que ahora se leen todos los candidatos de srcset y de los <source> de un <picture>. El parser sigue la especificación de HTML, porque partir por comas rompe las URL de algunos CDN, que llevan comas dentro.

Descargar sin poder crear un blob

En Manifest V2 una extensión tenía una página de fondo con su document, y descargar era hacer fetch, crear un blob y pasárselo a chrome.downloads. En V3 la página de fondo es un service worker, y ahí no existe URL.createObjectURL. Sin eso no hay blob que descargar, y menos un ZIP.

La salida en Chrome es un documento offscreen: una página invisible que la extensión crea con chrome.offscreen.createDocument y el motivo BLOBS. Hace el fetch de cada archivo, monta el ZIP con JSZip (añadiendo -1, -2… si dos archivos se llaman igual) y crea la URL del blob. Esa URL vuelve al service worker, que llama a chrome.downloads.download con la carpeta y el nombre que hayas puesto en las opciones.

Firefox no tiene documentos offscreen. Pero su fondo sí es una página con DOM. En vez de mantener dos versiones de la descarga, saqué toda la lógica a un procesador que no sabe dónde vive. Solo recibe la función con la que tiene que hablar:

// En Chrome, entrypoints/offscreen/index.ts
const { handleZipDownload, handleSingleDownload } = createDownloadProcessor(
  (message) => browser.runtime.sendMessage(message),
);

En Firefox, el fondo crea el mismo procesador con una función que llama a sus manejadores directamente. Mismo código, mismos tests, dos transportes. La versión de Firefox ya compila como MV3, aunque todavía no está publicada.

Los archivos de un ZIP se piden uno detrás de otro, no en paralelo. Es más lento, pero cada petición necesita su propia regla de red, que es la siguiente decisión.

Reglas de red que no se escapan

Muchas webs comprueban el Referer antes de servir una imagen. Desde la página funciona, porque el navegador manda el correcto. Pero el fetch sale de la extensión, y la web responde con un 403.

Para eso está declarativeNetRequest. Antes de cada petición, el service worker crea una regla que pone a esa petición el Referer y el Origin de la página original y las cookies que el navegador mandaría a esa URL. La parte importante es la condición:

condition: {
  requestDomains: [urlObj.hostname],
  tabIds: [-1],
  resourceTypes: ['xmlhttprequest', 'media', 'other'],
}

tabIds: [-1] significa «peticiones que no salen de ninguna pestaña», es decir, las de la propia extensión. Y requestDomains es el host del archivo (con sus subdominios), no un dominio base calculado a mano.

No siempre fue así. La primera versión usaba reglas dinámicas, que persisten aunque cierres el navegador. Calculaba un «dominio base» que fallaba con dominios como co.uk y se aplicaba a todos los tipos de petición. En la práctica, una descarga podía dejar viva una regla que tocaba las cabeceras de tu navegación normal en ese dominio. Lo reescribí con reglas de sesión: solo el host del archivo, solo peticiones sin pestaña, limpieza después de cada fetch, un temporizador de respaldo por si esa limpieza no llega y un barrido de reglas antiguas cada vez que arranca el service worker. Tiene su propio archivo de tests, que comprueba que la regla se crea con esa forma y se borra.

Un service worker que se duerme

Un service worker se para cuando no tiene nada que hacer, y su memoria se va con él. Eso rompe más cosas de las que parece.

El progreso de las descargas. El popup, el panel de DevTools y los botones de Instagram pueden lanzar descargas a la vez, y los mensajes de progreso llegan a todos. Cada descarga lleva un id (crypto.randomUUID()) que el procesador devuelve en cada mensaje, y cada interfaz ignora el de las que no ha empezado ella. Para los botones de Instagram, que viven en un content script, el progreso tiene que llegar a esa pestaña concreta. Al principio lo reenviaba un listener registrado dentro de la descarga. Pero un ZIP grande pasa varios segundos en zip.generateAsync() sin mandar mensajes, el service worker se dormía, y al despertar el listener ya no existía. Ahora la pestaña de origen se guarda en storage.session, con el id de la descarga como clave, y eso sobrevive a los reinicios.

El estado del popup. El popup se destruye cada vez que haces clic fuera. Al volver a abrirlo pregunta al service worker cómo va la descarga y retoma la barra. Desde la 1.5.0 recuerda también lo que ya había extraído: los medios, los enlaces y las fuentes se guardan por pestaña en storage.session, cada tipo con su clave (tabCache:<pestaña>:media, :links, :fonts) para que dos guardados a la vez no se pisen. El service worker borra lo de una pestaña cuando navega, se recarga o se cierra, porque los data-devextractor-id a los que apunta dejan de existir.

La barra de progreso. Es lo que yo llamaría una tontería que costó más de lo que parece. Si una descarga terminaba con algún fallo, el aviso de «completada con errores» se quedaba fijo y parecía que la extensión se había colgado. Ahora el resultado se borra solo a los pocos segundos, y el progreso se reinicia al lanzar cada descarga para no arrastrar el «14/14» de la anterior.

Sustituir en vivo y poder deshacerlo

El reemplazo visual es lo que más uso con clientes: soltar una imagen sobre la tarjeta del logo y ver la web con otro logo al instante. La regla de partida era que todo cambio se pudiera deshacer y la página quedara exactamente como estaba. El motor está en utils/visualReplacementEngine.ts y se apoya en tres piezas.

DomSnapshotter guarda el estado original antes de tocar nada, con el propio elemento como clave: src y srcset de cada <img>, el srcset de cada <source>, el poster de los vídeos, background-image y mask-image, y, en los SVG inline, su contenido y su viewBox. Guarda también si el atributo existía, porque restaurar un atributo vacío no es lo mismo que quitarlo.

Con esa foto guardada, el motor aplica el cambio. Un SVG inline no se puede convertir en un <img> sin romper la maquetación, así que se vacía y dentro se pone un <image href="..."> que ocupa todo el viewBox. Los pseudo-elementos fueron la parte divertida: un ::before no tiene nodo en el DOM ni estilo propio que tocar desde JavaScript. La solución es una sola hoja de estilos con reglas que leen variables CSS:

[data-devextractor-visual-replacement]::before {
  background-image: var(--devextractor-before-background-image) !important;
}

Para cambiar el ::before de un elemento, se le pone el atributo y se le da valor a la variable. Para deshacerlo, se quitan las dos cosas.

DomMutator hace el camino de vuelta, atributo por atributo. MutationWatcher, un MutationObserver, aplica el cambio a lo que aparece después mientras el reemplazo está activo: un carrusel que añade diapositivas, una imagen que llega tarde.

En las webs de una sola página, el motor escucha los cambios de ruta (parchea history.pushState y replaceState, y escucha popstate y hashchange). Al cambiar de ruta no intenta mantener los cambios: lo restaura todo. Una imagen sustituida en la portada no tiene por qué tener sentido en la siguiente vista, y dejar cambios sueltos donde nadie los ha revisado es peor que volver a aplicarlos.

Leer los datos, no la pantalla: Instagram

Instagram no está pensada para que una extensión la entienda desde fuera: sus clases CSS se generan solas y sus textos cambian con el idioma de cada usuario. Yo no lo uso, pero vi que mucha gente se quejaba de que las extensiones para descargar de Instagram ya no funcionaban, y quise ver si se podía hacer bien.

La información buena (la URL del vídeo en máxima calidad, todas las historias de un usuario, la foto de perfil grande) no está en el DOM, sino en los datos que la web carga. Hay dos content scripts que trabajan juntos. Uno corre en el mundo MAIN, el mismo JavaScript que la página, desde document_start, y lee esos datos, también los que vienen metidos en el HTML inicial. El otro corre en el mundo aislado de la extensión, recibe los datos por postMessage y coloca los botones dentro de un shadow DOM para que los estilos no choquen.

Ahí apareció un problema de orden: el script aislado se carga mucho después, y todo lo que el otro anunciaba antes se perdía. Lo arreglé con un intercambio de petición y respuesta. Cuando el script aislado empieza a escuchar, pide todo lo capturado hasta entonces.

Para colocar los botones, lo fácil sería buscar la barra de acciones por el texto de sus botones («Me gusta», «Comentar»). Eso solo funciona en un idioma, y las clases cambian. Así que se detecta por estructura: un <section> con al menos dos [role="button"] que contengan un <svg>. Los contadores de likes también son botones, pero no tienen icono, así que no cuentan. Y como un <section> que envuelve todo el post también contiene esos botones, de los candidatos se queda con el de menor área en pantalla.

En el feed, el botón aparece al pasar el ratón. La primera versión tenía un MutationObserver sobre todo el documento y un listener por post, en una página con scroll infinito. Ahora es un único par de mouseover y mouseout delegado en el documento, y la comprobación de qué reel está activo se hace como mucho una vez por fotograma.

En la 1.5.0, TikTok sigue la misma idea: leer los datos de la publicación en vez de la pantalla.

Cómo sé que funciona

Hay 563 tests en 57 archivos, con Vitest y happy-dom. Cubren:

  • el parser del DOM (con el srcset y la carga diferida), el recorrido de shadow DOM y la caché por pestaña;
  • el motor de reemplazo, con estilos calculados simulados para los pseudo-elementos;
  • el enrutado de mensajes del service worker, las reglas de red, las descargas simultáneas, la descarga en Firefox, el menú contextual y las opciones de nombre y carpeta;
  • casi todo lo de Instagram.

Un test comprueba que el inglés y el español tienen exactamente las mismas claves, para que no falte una traducción en silencio. Encima hay tests E2E con Playwright que cargan la extensión de verdad en Chromium y prueban el reemplazo sobre páginas de prueba. En cada push a main, GitHub Actions instala dependencias, pasa la comprobación de tipos con vue-tsc, los tests y la build.

Trabajo con IA y con un método: antes de cada cambio grande escribo una especificación, con lo que quiero, lo que no y las alternativas descartadas. El diseño, las specs y las reglas son míos; la IA implementa y yo verifico cada cambio.

Lo que queda

  • Publicarla en Firefox. La build ya es MV3, con su id de Gecko y sin recogida de datos declarada. Falta el paso de la tienda de Mozilla.
  • Más E2E. Hoy las pruebas de navegador cubren el reemplazo y los idiomas. Las descargas y la extracción en iframes solo tienen tests unitarios.
  • Rendimiento en páginas enormes. La galería pinta todas las tarjetas. En una web con miles de imágenes convendría virtualizar la lista.
  • El chino. La traducción existe, pero sigue oculta hasta que alguien la revise.

El código es privado. Si quieres verlo o hablar de cómo está hecho, escríbeme. La extensión está en la Chrome Web Store.
